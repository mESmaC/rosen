# SPEC.md · Rosen

Rosen is a version control system built so that many coding agents can work on one project at the same time: 100 agents in v1 and up to 1000 later. Rosen is two programs: a **server** that holds the project and does the expensive work, and a thin **client** that agents and humans use. Rosen is the source-control layer under [Velocity](https://github.com/mESmaC/velocity), the parallel agentic IDE. Where a cleaner or faster Rosen design needs Velocity to change, Velocity changes (§9).

- **Status:** draft, 2026-11-11. Written from the spec interview, then revised after reviewing the prior art below. Revised 2026-11-12: one server for agents on many machines, with AIRC served by Rosen and zero-touch enrollment (#25); snapshot ignore rules (#28); rebases applied when the workspace owner asks (#29); receipts reused across independent lands (#26); Rosen prepares pool workspaces (#31).
- **Optimizing for:** development velocity. Landing must be fast and must never lose work.

## 0. Prior art and what Rosen takes from it

| Source | Idea | Rosen |
|---|---|---|
| Anthropic, [Redesigning source control](https://www.anthropic.com/research/redesigning-source-control) (2,500 → 30,000 merges/day) | No global merge lock: a ref moves by compare-and-swap on one row | R8 landing |
| Anthropic | Server-side commits, rebases and merges; "nothing to push"; the client "can compute very little on its own" | D17, R2, R8 |
| Anthropic | Refs discouraged except main and release branches, because global state is a scaling problem | Changes are not refs (D18) |
| Anthropic | Changesets stored as deltas against the first parent, with derived data (blame, path history, ancestry) built from them | R11 history API |
| Anthropic | Tiered content-addressed caches: a per-node daemon, then regional, then authoritative, all answering the same RPCs | D8: each machine's daemon is tier 1 in front of the project's server; a hosted server takes that place later behind the same RPCs |
| Anthropic | Source control as a service, so many jobs need no checkout | Server-side workspaces, R11 |
| Anthropic | Post-merge and pre-deploy testing replace pre-merge gating at agent scale | D20, R12 |
| Anthropic | Review intent, with semantic approval rules (comment-only vs logic changes) | R7 review tiers |
| [CarterT27/scion](https://github.com/CarterT27/scion) (clean-room Rust reimplementation) | Landing = rebase a linear stack onto the ref, then versioned compare-and-swap, with retry and backoff | R8 |
| CarterT27/scion | `--json` with versioned output schemas; a per-node daemon on a local socket | R10, D8 |
| CarterT27/scion | Verification: an independent reference model, git differential tests, fault injection | §5; fits the proof fixture tables |
| CarterT27/scion | Measured result: git still checks out large full trees faster than a fetch-and-write client | R3: workspaces clone from a local store, not over the network |
| Google [Scion](https://github.com/googlecloudplatform/scion) (agent orchestration) | Agents have their own identity; notifications when work finishes or needs attention; "less is more", with agents learning the CLI from help text | Change owner identity (§2), targeted events (R9), self-describing CLI (R10) |
| Velocity SPEC §3.3, F5–F7, F14 | Receipts bound to an exact head and base, re-checks when the base moves, targeted rebases, 3-line overlap rule, warm pool, dependency waits and parking | R4, R6, R8; dependency waits become stacked changes (D19) |

**Not adopted:** Spanner, CockroachDB or S3 (v1 is one server with SQLite and a local volume); a virtual filesystem; and Anthropic's "always online, no offline" rule. Rosen keeps an offline fallback (D6).

## 1. Decisions

| # | Decision | Choice |
|---|---|---|
| D1 | Product | A VCS with a CLI and a server, which replaces git for high-concurrency agent workflows. |
| D2 | Concurrency model | Each agent works on its own **change**. Changes merge automatically at file level, and conflicts are stored as first-class objects instead of errors. |
| D3 | Landing model | **Optimistic landing, with no global queue or lock.** A land is a compare-and-swap of the base ref. This replaces the merge queue first chosen: Velocity and Anthropic both found queues too slow at agent scale. |
| D4 | Stack | Rust, in one Cargo workspace. |
| D5 | Storage | Objects are stored in **git format** (blobs, trees, commits), as loose content-addressed objects with no packfiles, so no repack or maintenance is needed. Rosen imports git repos and pushes landed history to a git remote. Storage sits behind a pluggable backend interface: the git-backed backend comes first, and a Rosen-native remote store comes later. |
| D6 | Workspaces | Two modes. **Local workspaces** are files on disk for agents' tools. **Server-side workspaces** have no checkout, and are read and written through the API. Both keep resource use bounded. Local workspaces keep working when the server is unreachable (offline fallback, R2). |
| D7 | Velocity integration | A `rosen-client` library crate that Velocity links directly. The `rosen` CLI is a thin layer over the same crate. |
| D8 | Server deployment *(revised)* | **One authoritative server per project**, reachable from every machine that runs agents for it (R14). Every machine runs a **daemon**, which `rosen-client` or Velocity can start. On the server's machine the daemon is the server. On every other machine it is the tier-1 object cache in front of the server, answering the same RPCs, so workspaces materialise from a local store. A hosted server can later take the authoritative role behind the same RPCs. |
| D9 | Check runner | Checks run **outside** Rosen: Velocity's build queue, PR duty, or any other client. Before-land checks submit a **receipt**; post-land checks submit typed results. Rosen validates them and runs no builds. |
| D10 | Coordination *(revised)* | **Rosen owns all coordination state**: path state (each change's live edited paths and line regions, and path claims) and the project's AIRC channel (task claims, events, messages and ledgers, R13). Velocity keeps AIRC's agent tools and view, and calls Rosen for every one, so every machine sees the same channel. |
| D11 | Platforms | v1 is tested and shipped on Windows 11. The code stays portable, and Linux and macOS are best-effort until a later milestone. |
| D12 | Review | **Rosen-native review**: comments, approvals and receipts are Rosen objects. GitHub receives landed history as a mirror and is not in the landing path. |
| D13 | Metadata store | Embedded SQLite in WAL mode, one database per server. |
| D14 | Scale target *(revised)* | v1: at least 100 concurrent changes on one project, from agents on several machines, typically 30–40 agents per machine (see §5). |
| D15 | Landed history | **One commit per change**: the change's final tree, with trailers for the change ID, receipt and approval. The agent's own commits stay in Rosen and are never rewritten. The commit's only parent is the base it landed on, or the preceding layer's landed commit in an atomic stack land, its author is the change's owner as `<nick>@<machine>` and its message is the change's newest `rosen commit` message. Its last paragraph holds git trailers: `Rosen-Change: <change ID>`; `Rosen-Receipt: <check set> <head> <base> <nick>@<machine>`, the receipt the land counted with its submitter as nick plus machine (R14), shared by every layer of an atomic stack land, omitted when none was needed; and one `Rosen-Approved-By: <nick>@<machine>` per approval that holds. `rosen log` shows them, including the older 3-field receipt form `<check set> <base> <nick>@<machine>` that lands wrote before the head was recorded. |
| D16 | Workspace lifecycle | **Rosen owns it**: creation, a warm pool, and deletion behind a guard. |
| D17 | Write-through snapshots *(revised)* | Every workspace write is snapshotted to the server automatically and within seconds, like jj's working-copy commit. There is no push or sync step. An edit that exists only on the client is the exception (offline, or inside the snapshot window), not the norm. This makes the deletion guard simple, gives the server live edit regions, and lets the server do every rebase. |
| D18 | Changes are not refs *(revised)* | The base (and later, release refs) is the only ref. A change is a row in the metadata store, with no branch name to create, delete or collide. |
| D19 | Stacked changes *(revised)* | A change can sit on top of another unlanded change instead of waiting for it to land. A request to land an upper change includes its unlanded ancestors atomically, bottom first (R8 step 3). When a lower change lands separately or updates, the server rebases the upper one automatically. This replaces Velocity's dependency waits and parking for most cases. |
| D20 | Landing gate | **Project review mode.** `review = "after-land"` needs only a clean merge and compare-and-swap; neither approval nor receipt gates landing. Build/lint and full tests run after landing. Both failure kinds are bisected and recorded; only broken builds revert in this mode. The default `before-land` retains approval, pre-land build/lint receipts, and full-test auto-revert (R7, R8, R12; owner decision #365). |
| D21 | Network access and enrollment *(new)* | The server listens on a network listener with TLS as well as the local transport. Machines join with **join keys**, with no login, monitor or remote desktop on the joining machine. Each machine gets its own revocable credential. Every agent on a machine works under that machine's credential, and Velocity names the agent and its role (R14). One enrollment adds a machine to both Rosen and Velocity. |

Defaults set during spec writing. These follow from the decisions above, and changing one is a product decision:
- **Transport.** Each daemon listens on a local transport for its own machine's clients: a named pipe on Windows and a Unix socket elsewhere, limited to the OS user. A client refuses an endpoint served by another OS user, since another user can create the endpoint first. The server also listens on a TCP port with TLS for enrolled machines' daemons (R14). The protocol is versioned and does not assume a local peer.
  - On Windows, an access-denied server-user check refuses the connection and names elevation or another user as possible causes; it suggests stopping one's own daemon and restarting it from a non-elevated shell.
- **Events.** The server pushes events to subscribed clients. Clients never poll.
- **Garbage collection.** v1 never deletes objects from the store.

## 2. Concepts

- **Project.** One repository held by one server. It has one **base** ref (for example `main`), which only a land can move.
- **Machine.** A computer enrolled in a project (R14). It holds its own revocable machine credential and runs a daemon that caches objects for its workspaces.
- **Channel.** The project's AIRC channel, served by the server (R13): task claims, events, messages and ledgers.
- **Change.** One agent's unit of work. Each change has:
  - a stable **change ID**;
  - an **owner** (agent identity: its machine and the nick Velocity gave it, R14);
  - a **parent**: either a base commit or another change (stacked);
  - an ordered list of commits and a current **head** tree;
  - a state;
  - any stored conflicts.

  States: `open` → `ready` → `landed`, or `abandoned`. `ready` means the owner asked to land.
- **Snapshot.** An automatic commit of a workspace's current files. Snapshots are made by the client from file writes and stored on the server (D17). Explicit `rosen commit` messages are named snapshots.
- **Stack.** A chain of changes, each a parent of the next. One land request includes the chosen change and its unlanded ancestors, with one commit per change, chained bottom first, and one compare-and-swap.
- **Workspace.** The files a change is edited in. Each workspace belongs to exactly one change, and is either **local** or **server-side**.
- **Conflict.** A stored object recording the base, ours and theirs for a region that did not merge automatically. A change that has conflicts cannot land.
- **Receipt.** A record that the required checks passed on one exact merge result. It records a signed `(change head, base commit, check set)` binding and the server-computed tree it checked. A trusted receipt for the current check set counts whenever that tree equals the current merge result, even after its head or base changes.
- **Approval.** A reviewer's approval of a change at a given head. It gates landing only in `before-land` projects.
- **Review coverage.** Each landed commit starts `unreviewed`; agents mark it `reviewed` or `issues-filed` (wire value `issues_filed`) without gating development. A repaired land starts fresh.
- **Post-land failure.** A durable record of a confirmed culprit, its change, check kind (`build` or `test`), failure output, and any inverse commit (R12).
- **Path claim.** A change's declared intent to edit a path or glob: a notice by default, reporting concurrent work. An opt-in **exclusive claim** uses first-claim-wins. Other changes may record a **share** (they edit it too, knowingly) or a **wait** (they hold off until claims are released).
- **Edit regions.** The paths and line ranges a change has modified relative to its parent. The server computes them from snapshots.
- **Overlap.** Two changes overlap when they claim the same path, or their edit regions in one file touch or sit within 3 lines of each other. Per-project configuration lists **generated files** and **registration lists**, which never count as an overlap.
- **Build unit.** A part of the project that builds on its own, together with the units it depends on. By default each package of a Cargo workspace is a unit, read from the workspace's manifests. Project configuration can list units instead, as path globs with their dependencies.
- **Workspace-wide inputs.** Paths every unit's build reads:
  - the root manifest and lockfile;
  - toolchain files and build configuration (such as `.cargo/`);
  - CI config;
  - the project configuration itself;
  - any other path that lies in no unit and is not prose.
- **Reach.** The units a change can affect: the units holding the paths it changed, plus every unit that depends on one of them, directly or through others.
  - A prose-only change (R7) reaches no unit.
  - A change to a workspace-wide input reaches every unit.
- **Independent.** Two changes are independent when their reaches share no unit. Then no unit's build sees both changes.
- **Project configuration.** The file `rosen.toml` at the repository root. The server reads it from the base, never from a change, so a change takes effect only once it lands.
  - Top-level `review` selects `before-land` (default) or `after-land` (R7, R8, R12).
  - It lists generated files, registration lists and sensitive paths as path globs, the pre-land and post-land check sets (a name and the commands checkers run), the warm pool size and the mirror remote. Each part is optional and has a default: no paths, check sets named `pre-land` and `post-land` with no commands, a pool of 4 and no remote.
  - `ignore` lists untracked paths snapshots skip (R2), in `.gitignore` syntax from the repository root, such as `target/`. It ranks below every `.gitignore` file. A workspace records the base's list when it is made or a rebase is applied, so a watcher started offline skips the same paths and a change cannot alter what its own snapshots skip.
  - `[prepare] commands` lists the prepare commands daemons run in ready workspaces (R3). The configured `warm_pool.size` is each daemon's target, read again after every land, unless a pool-size request has raised or lowered it since the daemon started.
  - Each ignore line and prepare command is one non-empty line with no control characters.
  - Optional `[build_units.<name>]` tables contain `paths` globs and `dependencies` unit names; absent units are discovered from Cargo workspace manifests, including target, build and dev dependencies. `workspace_inputs` adds shared input globs. Unknown dependency names conservatively reach every unit.
  - Unknown keys are refused, so a misspelt key cannot drop a list silently.
  - An invalid file never takes effect. The configuration in force is the one in the nearest first-parent ancestor of the base whose file is valid, or the defaults. The change that fixes the file still lands under the last valid configuration.
  - `rosen config show` prints the configuration in force and why the base's file was refused, if it was.

## 3. Architecture

| Crate | Holds |
|---|---|
| `rosen-core` | Data model: changes, stacks, conflicts, receipts, reviews, claims, regions. Pure logic, with no I/O. |
| `rosen-store` | The storage backend interface and the git-format loose-object backend. |
| `rosen-platform` | Narrow OS primitives with safe handle interfaces, including verified Windows file disposition. |
| `rosen-merge` | Three-way file merge, conflict objects and overlap detection. |
| `rosen-server` | The daemon: protocol, the SQLite metadata store, snapshots, server-side rebase, landing, claims, review, events, the AIRC channel, history queries, server-side workspaces, the git mirror push, the network listener and enrollment. On a machine that is not the server, the same daemon runs as the object cache that forwards to the server. |
| `rosen-client` | The public library API Velocity links: daemon discovery and start, joining a project, workspace materialisation, the file watcher and snapshotting, applying server rebases, and the offline journal. Its session runs every step of an agent's flow under the agent's identity, and its channel membership runs every AIRC tool under the member ID and nick Velocity gave it (§5). |
| `rosen-cli` | The `rosen` binary, a thin layer over `rosen-client`. |

- **Client–server asymmetry.** The server does every merge, rebase, landed commit and history query. The client materialises files, watches them, and uploads snapshots. Clients never run merge logic.
- **Topology.** One authoritative server per project. On every other enrolled machine, the daemon serves its clients over the local transport, answers object reads from its own cache, and forwards every other request to the server. Refs, claims, the channel and every other piece of mutable state are read and written only on the server, so no machine can fall behind or move ahead of it.
- **Metadata store.** SQLite in WAL mode, on the server only, holds changes, stacks, claims, regions, receipts, reviews, conflicts, workspace records, the channel, enrolled machines and the base ref. Every ref move and every claim is one transaction, and a crash in the middle leaves the store either before or after it, never between.
- **Metadata initialization.** Each server metadata connection enables WAL, full synchronous durability, a bounded busy timeout and foreign keys. The core change, snapshot, claim, conflict, review and landing tables are installed together in one transaction, recorded by SQLite `user_version`. Existing unversioned rows are preserved; a database with a newer schema version is refused. Module-owned derived indexes and event tables are initialized by their services.
- **Object store.** Git object format, stored loose and content-addressed. The server's store is authoritative. Each other machine's daemon keeps a store of the objects its workspaces use, filled from the server on demand and shared by every workspace on that machine. For a sparse workspace the daemon fetches every tree but only the blobs under its chosen paths, and records the trees it stored without all their blobs, so a later fill for a wider selection fetches the rest. Objects are immutable, so any cache tier can hold them without coordination.
  - Cache fills verify the selected descendants even below a previously complete tree. Cache object-read RPCs refetch and repair a corrupt stored copy from the server; an unreachable upstream or corrupt authoritative copy remains an error (#363).
- **Protocol.** Versioned, framed request/response plus one event stream per client. The same protocol runs over the local transport and over the network listener.

## 4. Features

### R1 · Repository import and git mirror
- `rosen import <git repo>` loads a git repository's history and makes its default branch the base.
- After each land, the server pushes the base to the configured git remote (for example GitHub). The push runs after the land commits and off its critical path. A failed push is retried and reported as an event, and never blocks or undoes a land.
- A push to the mirror is a fast-forward and never a force-push.
- `rosen import --mirror <remote>` names the remote, a URL or a path. It is kept in the metadata store, so it survives restarts.
- A remote named in the base's project configuration replaces the stored one at the next push. Removing it from the configuration keeps the last remote.
- A configured remote must be a network remote: an `https://`, `ssh://` or `git://` URL, or an scp-style `[user@]host:path` ssh address. The configuration is repository content, so a local path, a remote helper (`<helper>::…`) or a URL with credentials in it makes the file invalid. Only `rosen import --mirror`, which the operator runs on the server, can name a local path.
- One background task on the server does every push. It pushes the base tip, so lands made during a push go out with the next one. It also pushes at server start, so a push a crash interrupted still happens.
- Each failed push publishes a `mirror` event with the error and the retry delay. Retries back off from 1 s to at most 5 min. A push the remote refused, for example because the mirror has commits the base lacks, is marked `rejected`: only a person can fix that. The first push that succeeds after failures publishes a `mirror` event too.
- **Accept when:** a repo imported and then landed on shows the same history in `git log` on the mirror, with one commit per change and its trailers.

### R2 · Changes, snapshots and offline work
- `rosen change new [--on <change>]` creates a change on the current base, or stacked on another change, together with its workspace. The change ID stays the same for its whole life.
- **Write-through snapshots.** The client watches the workspace (`ReadDirectoryChangesW` on Windows) and uploads a snapshot within 2 s of the last write, plus on `rosen commit`. A snapshot sends only the changed blobs. Files of any size are carried: a blob too large for one protocol frame is uploaded, and fetched by a machine's cache, in slices, and the server stores it only once its bytes hash to its ID. The client hashes such a file as it reads it and sends it from disk in slices, and the offline journal stores and replays it the same way; a file written again while its snapshot is sent or journaled fails that snapshot's hash check, and the next snapshot takes it at its new content. The server and caches stream such a blob through disk, never holding it whole in memory: the server hashes and stores an upload from its staging file, serves slices from one checked copy instead of rereading the object per slice, and a cache stores a fetched blob slice by slice.
  - Before acknowledging a snapshot, including an unchanged tree, the server checks its objects and returns missing or damaged IDs as repair hints. The client resends matching prepared or workspace bytes, including unchanged blobs, then retries. Recovered bytes stay with a pending journal record if sending or replay fails. Newer workspace bytes are never substituted for an older ID; unavailable repair bytes leave an error and the path is read again on the next attempt. Large-object verification and repair stream their bytes (#363).
- **Held files.** A file the watcher cannot read because another process holds it open, such as a running executable or an exclusively opened database, does not hold back other writes. The snapshot keeps that file's last stored content, reports it, and the watcher reads it again each second until it can. A file larger than one 16 MiB frame, which is hashed and then sent from disk, is treated the same way when it is still changing after being hashed a few times, as a growing log or a database written without pause would be; its last stored content stands until it holds still for one read. `rosen commit` and workspace deletion (R4) read every file, so a held file fails them with its path.
- **Ignored paths.** Snapshots skip paths matched by the workspace's `.gitignore` files and by the project's ignore list (project configuration), such as build output (`target/`, `node_modules/`). An ignored path is never uploaded, never counts as an edit or an overlap (R6), and never blocks deletion (R4). Writes to ignored paths do not delay a snapshot.
- **Offline journal.** When the server is unreachable, snapshots go to a local append-only journal and are uploaded in order on reconnect. Each captured snapshot retains its bytes even after later writes or a client restart. Records live under `.rosen/journal`, with their blobs in a workspace-local object store, and each record is removed once the server acknowledges it. While the server is reachable and no record waits, a snapshot goes straight to the server without a record. While the server stays unreachable, the watcher tries again after 1 s, doubling the pause after each further failure up to 16 s; a retry only uploads what the journal holds, without reading the workspace again, and a new write is captured on the usual schedule whatever the pause. Each replayed record is reported as its own snapshot. A record the server refuses for good, as when the change landed or was abandoned while the client was away, halts the journal: that record and every later one stay, later snapshots are journaled behind them without uploading, and each attempt reports the refusal, so the deletion guard (R4) keeps the workspace. The halted journal replays again once the change is open and is no longer as the server showed it just before the refused records were sent: reopened, as after a post-land revert (R12), or given a new head, as by a server rebase. Until then an attempt only reads the change and uploads nothing, since the same change would refuse the same record again. The watcher stops on a halt for a closed or missing change; on any other refusal it keeps capturing writes and retries on the usual schedule. A record the server fails with an internal error, which may be a passing store or database failure, stays first in the journal and the watcher keeps retrying it on the same schedule; a retry of a tree whose objects the server already took sends only the snapshot request again. A workspace-local tree cache allows the watcher to start offline. A workspace-local stat cache keeps each tracked file's size and modification time with the blob it held, recorded when the workspace is materialised and after each full scan, and only for times at least 2 s old, as a later write in the same clock tick could leave a newer one unchanged. A full scan by a new writer, such as `rosen commit` or a watcher start, rereads only files whose size or time differs from it, instead of every tracked file. Snapshot writers take turns: a second writer, such as `rosen commit` while the watcher runs, waits for the first instead of failing. A writer that finds another writer's snapshot captured since its own scans every file, so it never stores an older version of a file the other stored. A named snapshot whose answer was lost is looked up before it is replayed, so its commit is recorded once. Landing requires the server.
- Snapshots and commits belong to the change and are never rewritten.
- **Applying server rebases.** When the server rebases a change (R5, R8, D19), the rebased tree is written into a local workspace only when the workspace's owner asks. The client exposes `rebase_change` to compute and persist a server rebase, preserving all snapshot commits; `rosen rebase` runs it and, inside the change's workspace, applies it. A rebase that conflicts still moves the change onto the base: its new head holds the conflict markers and its conflicts are stored (R5). Snapshots sent before local application name their workspace basis; their edits are merged onto the rebased head while their original commit trees are kept. Such a snapshot is never refused for a conflict: the head holds markers for edits that do not merge, with the snapshot's side as `ours`, and those conflicts are stored (R5). The client exposes `apply_rebase(root, owner)` to apply the stored tree explicitly. Applying requires paused tools and watcher, refuses unstored edits and pending offline snapshots, and preserves ignored output. Velocity asks at the agent's step boundary, or while the agent is parked, so files never change under an agent mid-step (§9).
  - The client first flushes a final snapshot, then writes the rebased files, with conflict markers for any stored conflict (R5).
  - If the files on disk differ from that snapshot, it refuses and leaves the workspace unchanged, and the owner asks again after the next snapshot.
  - A server rebase never writes into a local workspace by itself. A server-side workspace (R3) takes the rebased tree directly.
- **Accept when:** a change's commits survive any number of rebases unchanged; a write is on the server within 2 s while the server is reachable; and applying a rebase never overwrites a write that is not in a stored snapshot.
  - Correctness tests wait for the snapshot with a generous hang timeout and verify its stored bytes and ignored paths. The 2 s write-through budget is measured by the stress benchmark, not asserted against wall-clock time in unit or integration tests running under build load (#371).

### R3 · Workspaces
- **Local workspaces** are materialised from the local store:
  - **ReFS block clone** (Windows Dev Drive, or any ReFS volume) is the fast path, and true copy-on-write. Rosen recommends putting workspaces on a Dev Drive.
  - Otherwise a **parallel plain copy**.
  - **Hardlinks are never used** for files in a workspace. Agents' tools often write files in place, so a hardlink would let one workspace's write corrupt the shared object and every other workspace that links to it.
  - Sparse checkout lets a workspace hold only chosen paths. A chosen path holds itself and everything under it.
  - A workspace is built in a hidden directory beside its destination and renamed into place when complete, so a crash never leaves a partial workspace.
  - The hidden directory's name carries the building process's id, and a marker file beside it shows it is unpublished; the marker goes when the directory is published or removed. A later materialisation beside it, by a client or pool worker under the load limits, removes a marked directory in the background once its process no longer runs, so a crash mid-build leaves no lasting partial copy. The directory's bytes stay charged to the disk budget until they are deleted. A directory without a marker is never removed. Rosen reserves that name form (`.<name>.rosen-partial-<pid>-<n>`): materialisation and pool takes refuse it as a destination.
  - A block clone is checked by hashing one cloned file against its blob before the rest are cloned. On a mismatch, or any clone failure, the workspace is written by plain copy instead. Untracked output the clone carries at a path the new tree tracks gives way to the tracked file or directory; it is not a clone failure.
  - On Windows a symlink in the tree is written as a plain file holding its target, as git does by default there.
- **Server-side workspaces.** Files live on the server, and clients read, write, list and diff them through the API, with no checkout. Writes become snapshots directly. `workspace_read` reads a file or lists a directory on the current change head; `workspace_diff` compares it with its parent. `workspace_write` writes bytes (new files are regular files and existing modes are preserved), or deletes a file with `None`, and returns its stored snapshot. Parent directories are created as needed and empty directories are pruned on deletion. Files of any size are carried: a write too large for one protocol frame uploads its blob in slices first and then names it, and a read of such a file, here or through the R11 file read at any revision, fetches it in slices and checks it against its ID. Concurrent writes each build on the preceding head. Reads and writes follow server rebases directly. Rosen recommends them for jobs that touch few files, such as reviewers, check runners and doc edits.
- **Warm pool.** Each machine's daemon keeps N ready local workspaces at the tip of the base (default 4, 0 turns the pool off). Velocity can raise N for a launch, up to the configuration's limit of 1000. Only the daemon's own machine may resize or take from its pool: the server refuses both from network peers. After each land the daemon brings ready workspaces up to the new tip by rewriting only the changed files, reading only the directories that changed. Taking one is atomic, so two changes never get the same workspace. A take prefers a prepared workspace and reports whether it is prepared. When no ready workspace or template holds the change's tree yet, as when lands outpace the daemon, the take brings another ready workspace to that tree by rewriting only the files that differ, and reports it unprepared. Each ready workspace already holds its tree and stat caches (R2), so a take only renames, marks and registers it, whatever the tree's size, and its first snapshot rereads only files written since.
  - A rename works only within one volume, so ready workspaces live on the volume workspaces do. The daemon keeps them in its data directory unless started with `--warm-pool-dir <DIR>` (default `$ROSEN_WARM_POOL_DIR`), which names a directory on the workspaces' volume, such as the Dev Drive. The daemon uses only a subdirectory of it named for its data directory, so daemons of several projects can share one setting and the daemon never removes anything else there. A take into another volume than the pool's is not served: the client materialises the workspace itself, and its report says why the pool was not used.
- **Prepared workspaces.** Project configuration lists **prepare commands**. These are steps whose results don't depend on the workspace's path or its agent, such as installing pinned toolchains, fetching dependency caches (`lake exe cache get`) and a prebuild (`cargo build --workspace`). The daemon runs them in each ready workspace, so an agent's first build compiles only what it changes.
  - Prepare commands run for one workspace at a time per machine, at below-normal priority, so agents' own builds go first. A machine runs one daemon per project, so each prepare takes a turn in the machine's run queue, in its last class (Run queue below).
  - A checker that builds a change's merge result in a folder of its own can start from the pool too: the client asks for the merge result's tree and gets a ready workspace brought to it, with the build output its prepare left, as a plain build tree that is no workspace. Its first build then compiles only what differs from the base. With no pool that can serve the folder, the tree's files are written plainly.
  - After a land, the daemon runs them again in each ready workspace unless every change landed since it was prepared is prose-only (R7).
  - A workspace whose prepare failed is retried when the base next moves. It can still be taken, and the take reports it unprepared.
  - A prepare that leaves a link or a file where the base tracks a directory makes its workspace unsafe to hand out, so that workspace is removed. The daemon then stops running the prepare at that base: its workspaces are handed out unprepared, as after a failed prepare, until the base or the prepare commands change.
  - Each command runs through the platform shell (`cmd /C` on Windows, `sh -c` elsewhere) from the workspace root, and stops the prepare at its first failure. A command still running after an hour counts as failed.
- **Template on ReFS.** On a ReFS volume the daemon keeps one prepared **template** workspace at the base tip. It makes ready workspaces, and any workspace beyond the pool, as block clones of the template, including its ignored build output (R2). Each starts prepared at almost no copy cost. A cloned file keeps its source's modified time: build tools compare those times, and a clone stamped with the moment it was made would have its whole build output rebuilt. Until the template is prepared at the tip, ready workspaces stay as they are and the take reports them unprepared. Without ReFS, each ready workspace is prepared on its own.
- **Per-agent setup stays with the owner.** Steps that depend on the agent, its credentials or its final path run after the take, by whoever took the workspace. Velocity copies untracked files such as `.env`, links skills and runs its after-take setup command (§9). Rosen never stores those files.
- **Run queue.** Heavy commands on one machine take turns, a few at a time, so they keep the cores busy and finish sooner than many running side by side. The queue is one folder per machine and user, with operating system file locks: it needs no daemon, and a crashed waiter or runner leaves the line when its process dies.
  - A run has a class, most important first: `landing` (the checks a land waits on), `build` (an agent's own builds and tests), `verify` (the full tests after a land, and bisection, R12) and `prepare` (the warm pool's prepare commands).
  - Each class has a number of **slots**, and that many of its runs go at once. `landing` and `build` get one slot per 5 logical cores or per 8 GiB of memory, whichever gives fewer, and never under 2; `verify` and `prepare` get 1. A machine can set its own count for any class (below). A run starts when its class has a slot free once the earlier waiters of its class have taken theirs, no more important run is going, and nothing more important is ahead of it in line.
  - Default from a measured ramp (2026-11-14, one Windows 11 machine with 20 logical cores and 64 GiB, other agents' work running beside it): 1 to 4 clean `cargo build` runs at once, each through the queue in its own `build` slot and target folder. Rosen's workspace took 52.9, 63.1, 74.1 and 71.1 s of wall time, 1.0, 1.7, 2.1 and 3.0 times the work per second of one run alone; Velocity's (without the app crate) 43.3, 60.6, 89.8 and 104.8 s, 1.0, 1.4, 1.45 and 1.65 times. Throughput still rose at four for both, so that machine gets 4; free memory fell by under 2 GiB per added build, and never below 26 GiB. The ramp went no higher than 4, so the default claims nothing past it.
  - `rosen run --slots` prints each class's count, thread settings and process priority on this machine; `rosen run --slots build=6,landing=3` sets this machine's own counts, and `CLASS=default` goes back to the default. The counts live in the queue folder, so they hold for every project and process of this user on the machine. Waiting runs see a change on their next look, and a lowered count stops no run already going.
  - Commands started by `rosen run` default `CARGO_BUILD_JOBS`, `RUST_TEST_THREADS` and `LEAN_NUM_THREADS` independently to `max(2, logical cores / heavy slots)`, rounding division down. Heavy slots are the machine's configured `landing` plus `build` counts. Each value the caller set is preserved; defaults are calculated when the command starts.
  - A less important run that is already going is never stopped, and never holds a more important one back. So a landing check starts at once beside a prepare. On Windows, `rosen run` starts `landing` commands at `NORMAL_PRIORITY_CLASS`, `build` at `BELOW_NORMAL_PRIORITY_CLASS`, and `verify` and `prepare` at `IDLE_PRIORITY_CLASS`. Elsewhere it uses `nice -n 0`, `5` or `10` respectively. Children inherit the priority; a nested run keeps its ancestor's class and does not add niceness again.
  - Nothing waits for ever. After its class's patience (`build` 3 minutes, `verify` 2, `prepare` 10) a waiter stops yielding to more important classes and needs only a free slot of its own class. A stuck landing check cannot hold every agent's build, and steady agent builds cannot keep the tests after a land from running.
  - `rosen run [--class <class>] -- <command>` waits for the turn, runs the command and exits with its status; the class defaults to `build`. While waiting it prints its class, thread settings and priority alongside the runs ahead. A checker takes a turn through `rosen-client` for the whole of one check. The queue only schedules: a caller that cannot use it runs its command anyway.
  - A turn passes to the processes it runs: they get `ROSEN_RUN_HELD` set to its class, and `rosen run` beneath one runs at once instead of waiting behind its own ancestor. A script that queues its own steps can therefore be run through `rosen run` whole, and a prepare or check command that calls `rosen run` never waits on the turn it is part of.
- **Load limits.** Each daemon caps its machine's concurrent materialisations, and the server caps server-side workspace I/O; both queue the rest. The client caps local disk use. A request over a cap waits; it never fails or degrades another workspace.
  - A materialisation failure names the failing admission file and operation, or both staging and destination paths when publication fails, along with the underlying OS error.
  - Machine admission is shared by clients and pool workers through OS file leases under the daemon's data directory. Defaults are 4 simultaneous materialisations and a 100 GiB logical workspace-content budget; the server defaults to 8 concurrent workspace I/O operations. The library can initialize other positive limits. `rosen workspace limits` shows the machine's two caps, the materialisations running and the bytes charged, and with `--materialisations` or `--disk-gib` changes either cap; the change persists for every client and the pool, and requests already waiting see it on their next attempt. A lowered slot cap stops no running copy.
  - A request that has waited 5 s says why on its process's stderr (the CLI's for a client, the daemon's log for a pool worker; a daemon a client starts appends its stderr to `daemon.log` in its data directory, set aside as `daemon.log.old` once past 4 MiB, checked at start and every minute while it runs): no free slot, or the bytes it needs against those charged and the cap, and how to raise that cap. It repeats every minute or when the reason changes, and says when it is admitted. A request larger than the whole disk cap says so and waits until the cap is raised.
  - Disk admission reserves, before copying, the most logical bytes the build can leave: the target files, or for a block clone the source-template content plus the target files its tree does not hold unchanged, whichever is larger. A source on a volume that cannot block clone into the destination is not charged. Admission counts existing workspace files (including ignored output) and crash staging files, and keeps pool workspaces charged after a take. Deletion frees their budget. These limits control Rosen's workspace creation; agents' later filesystem writes are counted on the next admission scan.
  - One process per machine at a time scans workspace files, outside the admission lock, so admissions and pool takes never wait behind a directory walk. The next scan starts a second after the last, or after as long as that scan took if longer. A scan starts walks for at most 200 ms, workspaces measured longest ago first, so the request that runs it waits about that long plus one workspace's walk, and the scans cycle through every workspace in turn. Admission charges each workspace its last measured size, and a reservation no scan has measured yet its reserved bytes. A scan drops records of deleted workspaces, so the registry stays as large as the workspaces on disk. Blob sizes for a reservation come from object headers, without reading the blobs.
- **Accept when:** with the warm pool filled, a new prepared workspace is ready in under 2 s; an agent's first build in it compiles only what the agent changed; and two changes never share a workspace.

### R4 · Workspace lifecycle and deletion
- Rosen is the only thing that creates or deletes workspaces. Velocity calls `rosen-client` instead of `git worktree`.
- A workspace is deleted automatically when its change lands or is abandoned.
- **Deletion guard.** Before deleting, Rosen flushes a final snapshot. It refuses deletion while any of these is not stored on the server:
  - a write the watcher has seen but not yet snapshotted;
  - a journal entry that has not been uploaded;
  - a file whose content differs from the last stored snapshot, found by a final hash scan. Ignored paths (R2) are not scanned.

  The refusal names the files and keeps the workspace.
- On Windows, final removal hashes write-excluded file handles and deletes those exact objects while excluding concurrent renames. On Unix, best-effort removal opens files without following symlinks, verifies their stored blob IDs through those handles, isolates each selected file in a private directory relative to its opened parent, rechecks its device and inode against the held handle, rehashes it, and removes it with `unlinkat`. A replacement detected after isolation stays in that directory, named in the refusal, for recovery. Nonempty isolation directories always keep the workspace, even when ignore rules match them. Unix does not exclude writes through already-open file descriptors; its final hash detects changes completed before that read. Directories are removed only when empty; newly created files are retained. Cleanup interrupted after removing durable files keeps the remaining directory for recovery; an interrupted Unix isolation may require recovery of the named entry before retry. Other platforms retain the workspace with an unsupported-operation reason.
- A workspace whose change is closed or failed is kept until the change is explicitly deleted.
- Deleting a workspace removes only that workspace. Local workspace registrations survive daemon restart; the daemon retries guarded cleanup of landed and abandoned workspaces on startup and change events. Pending warm pool prepares (R3) never postpone it: the daemon acts on a change event as soon as the prepare command running at the time finishes. A refused cleanup retains the registration and records the reason on it, which `rosen workspace list` shows; it is retried on the next change event and on a timer that backs off from 1 s to 1 min. Cleanup passes on one machine run one at a time. A cleanup interrupted after removing verified files finishes on retry.
- **Accept when:** no sequence of crashes, deletions, offline periods and reconnects loses an edit that was written to a workspace.

### R5 · Automatic merge and conflicts
- The server merges three ways at file level and line level, against the merge base.
- Generated files listed in project configuration are regenerated, never merged. Registration lists keep both sides' additions.
- A region that does not merge automatically becomes a stored conflict on the change, which records base, ours and theirs. A local workspace shows conflict markers once the rebase is applied (R2). The markers are written as `git merge-file --diff3` writes them, in the file's line endings, with the change's side as `ours` and the base's as `theirs`. A rebase that conflicts, such as after a land refused for a conflict, stores the conflicts and gives the change a head on the new base whose conflicting files hold the markers, so the owner can keep both sides. Open conflicts never block a rebase, and a rebase never clears one. `rosen resolve` clears a conflict.
- **Accept when:** a clean merge never drops or duplicates a line that either side kept, and every non-clean region becomes a conflict instead of a silent pick.

### R6 · Path claims and edit tracking
- `rosen claim <paths…>` records notices for a change and never refuses because of overlapping work, including an exclusive claim. Its reply and a durable `claim` event name every other live change claiming, sharing or editing those paths, including generated files and registration lists. The event reaches those changes' owners so both sides learn of concurrent work.
- `rosen claim --exclusive <paths…>` opts into first-claim-wins: an overlapping claim on another live change refuses the whole request and names its holders. It refuses any pattern that covers a generated file or registration list, using the base's configuration. Existing stored claims retain their exclusive mode on upgrade. `share` still records concurrent editing, and `wait` lets an agent choose to hold off.
- Edit regions update from each snapshot. Ignored paths (R2) have no edit regions. The server derives the live path and region view from one captured head and parent; reverting a path to its parent removes its regions. Regions use zero-based, half-open parent line spans, with an empty span for an insertion. The view survives restart through the stored snapshot objects and change metadata. `rosen-client` exposes it through `Client::edit_regions`, including the captured head and parent tree IDs.
- An **overlap query** returns, for a change or a set of paths, every change that overlaps it. The channel (R13) and Velocity call it.
  - A claim or share covers every line of the paths it matches, so it overlaps another change's claim, share or edit there. A wait does not, because a waiter holds off. A set of paths in a query counts as a claim. A query that names a change and paths returns only that change's overlaps on those paths.
  - Post-land conflict probes use edit-region overlaps only (R8 step 4). Claims and shares still receive overlap notices, without moving their changes.
  - Edits are measured against the change's parent. Two changes on different parents are compared in one parent's lines, after carrying the other's edits across the lines both versions share. An added, deleted, binary or mode-changed file counts as edited throughout.
- These are AIRC's file claims: `airc_claim` files, `airc_share` and `airc_wait` record path claims, shares and waits here (R13). There is one claim record per path, not one in AIRC and one in Rosen. CLI claim, share, wait, release and status output uses v2 schemas for the new mode and concurrent-work fields; the catalog retains v1 (R10).
- Claims release when their change lands or is abandoned. Abandonment and removal of its claims, shares and waits commit together. Release transactions retain pending notifications until published, so a restart replays a wait's wake even after its record was removed. Delivery is at least once. A wait is then signalled by an event.
- **Accept when:** two concurrent default claims on `SPEC.md` both succeed and each owner learns of the other; two exclusive claims on one path never both succeed; release wakes a waiter once no other live claim remains on its paths.

### R7 · Review
- Review comments anchor to file, line and change head, and form threads with an open or resolved state.
  - A new thread anchors to a line of a file in the change's current head, and the server refuses a path that is not a file there or a line the file lacks. A comment that names the head it was written against is refused once the change has a different head. The anchor never moves; each reply records the head it was written at.
  - Open and ready changes take comments; after-land projects also accept them on landed changes. Anyone can resolve a thread. A reply to a resolved thread reopens it. Each comment, resolve and reopen publishes a `review` event.
- `review approve <change> --head <head> [--reviewer <agent>]` refuses stale heads and abandoned changes (also landed changes in `before-land` mode), stores the reviewer and timestamp, and publishes a `review` event. `review list <change> --approvals` lists durable approval history, including void approvals.
- An approval is tied to the head it approved. A new head by the author voids the approval. A rebase done by the server (R8, D19) keeps it, because it changes only the parent. A receipt likewise survives when its checked tree still equals the current merge result (R8).
- **Review tiers** follow Anthropic's semantic approval rules and Velocity F7:
  - The server tiers each change from its diff: prose-only, normal, or sensitive.
  - Sensitive paths are listed in project configuration and read from the base, so a change cannot lower its own tier. Sensitive matches take precedence, including removed paths.
  - Prose-only means all changed files are regular UTF-8 `.md`, `.markdown`, `.txt` or `.rst` files without NUL bytes on either side. Generated files, registration lists and configured workspace inputs take normal review. Other edits, including source comments and executable or symlink modes, conservatively take normal review. The diff is against the parent (the stack parent for a stacked change); an empty diff is prose-only.
  - In `before-land` mode every tier still needs an approval. In `after-land` mode no tier needs approval or a receipt.
- Velocity's PR duty reviews through `rosen-client`.
- `review mark <change> <unreviewed|reviewed|issues-filed>` records coverage on a landed change; `review landed [--state <state>]` lists it. Comments, threads, resolutions and approvals work on open and, in after-land projects, landed changes.
- **Accept when:** in `before-land` mode a change cannot land without an approval for its current head; in `after-land` mode an unapproved change lands and its review coverage remains visible.

### R8 · Optimistic landing
Landing is the core algorithm. No global queue or lock exists, and unrelated changes never wait on each other.

1. **Before-land mode:** a checker gets the server-computed merge result of a change onto base commit B, runs the project's **pre-land check set** (build and lint, D20), and submits a **receipt** for `(head, B, pre-land check set)`. A wholly prose-only stack (R7 tier) needs no receipt. The server stores the checked merge-result tree with each receipt, retaining the preview shown for that head and base so a concurrent parent update cannot substitute a different tree. A late receipt may name the older head shown in that recorded preview; storing it keeps its original checked tree. A preview that would bind a different tree to an already recorded head/base pair is refused until parent propagation or a rebase advances the head.
   - Each landing attempt reads the check-set name and computes the review tier from the configuration at that attempt's base, including retries after a lost compare-and-swap. The review mode is also read from that exact base, so a change cannot disable its own gates. Before-land prose-only changes still need approval and a clean merge.
   - **Signed receipts.** Every machine's daemon holds an Ed25519 receipt key, created on first use in its data directory, readable by the current OS user only, and never replaced. It signs each receipt a client on that machine submits, over the change ID, head, base, check set and submitter. The server takes the submitting machine from the connection's machine credential, never from the request, and refuses an unsigned receipt from the network. The request names only the submitter's nick, which may not contain `@`. The server records the submitter as nick plus machine: the enrolled machine's id, or `server` for the server's own machine. The stored receipt `rosen receipt submit` returns and the landed commit's trailer both show it. A joining daemon sends its public key with its enrollment or pending request, and the server binds it to the machine in the same transaction that issues the credential. A machine enrolled without one, before daemons sent it, has its key bound the first time the server accepts a signed receipt from it. Either way, a receipt signed with any other key is refused. A receipt submitted on the server's own machine is signed with the server's key. The server verifies the signature when it stores the receipt and again whenever a land decides on it: a receipt whose fields no longer match what was signed, or whose machine has since been revoked, does not count, and the change needs a new receipt.
2. `rosen land <change>` asks the server to land it. In one transaction the server checks:
   - every change in the requested stack has no conflicts and merges cleanly. In `after-land` mode it needs no approval or receipt, of any tier; the server writes the landed commit and compare-and-swaps the base it merged onto. It skips receipt lookup and all receipt reuse/re-check rules;
   - in `before-land` mode every layer also needs an approval for its current head, and only the top needs a valid receipt for the final merge result (unless the whole stack is prose-only); the following receipt rules apply only in this mode;
   - **same checked tree**: any trusted receipt for the top change and current check set whose stored tree equals the current merge result counts, regardless of its original head or base. A parent land and a server restack do not require a new check when the final tree stays identical;
   - **base unchanged** (the base still equals the receipt's B): with the checked tree unchanged it writes the landed commit chain and compare-and-swaps the base ref from B to the top commit;
   - **base moved**, with a different checked tree: the server merges again onto the new base and applies the **re-check rules**. For a stack, reuse first verifies that its current layers still produce the receipt's checked tree on the receipt's base, and computes reach over all those layers:
     - every change landed since B is **independent** of this change (§2), and the merge is clean → the existing receipt still counts. Each unit this change reaches has the same inputs the receipt checked, and every other unit is as the landed changes' own receipts left it;
     - otherwise, with a clean merge → a new pre-land receipt on the new merge result is required. A clean textual merge can still break the build. For example, a field one change adds can break another change's struct literal in a file the first never touched. Those two changes are not independent, because the second change's unit depends on the first's;
     - build units and workspace-wide inputs are read from the current base, so a change cannot widen its own independence. A change that edits them reaches every unit. A dependency the configuration misses is caught after landing by post-land verification and reverted (R12);
     - conflict → the change gets stored conflict regions with base, its own side and the incoming base side, and a `conflict` event naming the files, and the land is refused. The refusal names the stored files, including on a repeat request. If a snapshot moves the head or closes the change before routing commits, that attempt attaches nothing and the server decides again on the change's new head; a post-land conflict probe likewise merges that change again.
   - The ref move, every layer's landed-history insertion and every registry transition to `landed` commit in one SQLite transaction. The transaction rechecks every layer's head, state, parent, remembered merge basis, conflicts and required approval; a missing or moved input retries the attempt. A failed layer never lands only a prefix. Snapshots after that commit are refused, including before post-land recovery finishes.
   - If the compare-and-swap loses a race, the server retries the land itself with backoff, with the mode and gates at the new base (in before-land mode, as long as no new receipt is needed). A land is never applied twice.
   - A requester whose connection drops mid-land asks again on a fresh connection, starting the server if it is down. A repeat is answered `already_landed` with the landed commit, so a server crash never loses the answer or doubles the land.
3. A **stack** lands in one request: `rosen land <change>` includes all its unlanded ancestors and the change itself. The server writes one landed commit per change, chained bottom first, and moves the ref once by compare-and-swap. Before-land projects require approval on every layer and only one receipt, on the top's final merge result. `parent_unlanded` means a lower change cannot land (for example, it is abandoned, conflicted or unapproved), rather than requiring a separate land request.
   - The server remembers the parent tree each child was based on. A parent snapshot or server rebase automatically merges its new tree into live descendants in stack order, retaining each dependency, change ID and authored commit. Conflicts are stored on the child and stop propagation through that child until resolved. A restart resumes pending parent updates from the saved tree; workspaces apply the resulting head only when their owners ask (R2).
   - A legacy edited stack with no recoverable parent-tree basis is refused rather than merged against a guessed basis that could delete intervening landed work.
     - Its owner recovers it with `rosen change recover <change> <basis>`, naming the parent tree the change started from. The server accepts only a tree the stack's history recorded: a snapshot of the parent change, by commit or tree, or the commit the change's first snapshot followed. It never picks one itself and never replaces a recorded basis. Recovery refuses a legacy child with no authored snapshots: its head already supplies its exact implicit parent-tree basis. The parent's later edits are then merged in like any parent update, keeping every authored snapshot and storing conflicts on the child.
   - A stacked change's merge result (step 1) measures each unlanded change in its stack from that remembered parent tree, merging them bottom first onto the base. It is the same merge the atomic land performs layer by layer, so a child whose head has not caught up with its parent never reads the lands in between as deletions.
4. After a land:
   - the requester is answered once the transaction that moves the ref commits, the `landed` event is published and the changes stacked on the landed change are rebased, so a checker that asks for a child's merge result next sees the child on the new base. That transaction also records the land's post-land work as pending. The rest of the work below, which is releasing claims, the `released` event and probing overlapping edits, can follow the answer, and recovery finishes it if the server stops first;
   - each landed layer has its own pending post-land record, events and claim release, so recovery and R12 retain per-change history. Surviving descendants of any layer rebase onto the request's final tip;
   - claims are released;
   - the server rebases changes stacked on the landed change onto the new base, without rewriting commits (D19), with a `rebased` event. Their local workspaces are updated when their owners ask (R2);
   - the server probes changes whose edit regions overlap the landed change by merging onto the new base outside the change registry lock. Conflicts are stored and announced with a `conflict` event, without moving the head or parent. A clean probe installs nothing and emits no `rebased` event; each change moves at its own land or when its owner runs `rosen rebase`;
     - probe targets are saved before releasing the landed change's claims, so recovery reuses the same selection, including an empty selection. A selection that fails on what is stored, such as an unreadable project configuration at base, is logged and saved as empty. A busy database or I/O error is not saved: the post-land run fails and its replay selects again;
     - claim-only overlaps receive the `landed` notice through the ordinary event audience (R6, R9), without a merge. Generated files and registration lists remain excluded;
   - the mirror push is scheduled.
   - Post-land work that a crash or a failed step interrupts is replayed: at server start, and then with backoff whenever a land's post-land work fails. One land's failure never holds back another's. A land's post-land work runs at most once at a time, and a replay publishes the land's `landed` and `released` events only if the log does not hold them yet. A rebase only moves a change forward, and only from the head its merge read: a change already on the landed commit or a later base is left there, so a replayed or slower post-land run never moves it behind a newer base, and a snapshot stored meanwhile is merged again rather than overwritten.
- **Order** is set only between changes that overlap each other, or are stacked.
- **Accept when:** a clean after-land change lands with neither receipt nor approval in under 200 ms; a three-change before-land stack with approvals on every layer and one receipt on the top lands as three commits in one request in under 200 ms, and a child's checked receipt survives a separate parent land without a new check. The base only ever moves by a land whose merge is clean (and, in `before-land` mode, whose receipt and approval match), or by a server revert; a receipt is reused when its checked tree matches exactly, or under the independent-land re-check rule above; and a crash at any point leaves the base at either the old or the new commit. A land with 20 clean edit overlaps leaves all 20 heads unchanged, and the next land does not wait for their probes.

### R9 · Events
- A `rebased` event reports an installed rebase, including a stack restack or an owner-requested rebase. A clean overlap probe emits none. Claim-only overlaps receive the `landed` notice.
- The event types are `snapshot`, `landed`, `rebased`, `conflict`, `updated`, `review`, `claim`, `released`, `green`, `reverted`, `post_land_failure` and `mirror`.
- Each event is delivered only to subscribers it concerns: the change's owner, its reviewers, changes stacked on it, and the holders of overlapping changes or claims.
- An event's audience is fixed when it is published. An event about no change, such as `mirror`, goes to every subscriber.
- A subscriber names its agent. A subscription that names no agent is the project view: it gets every event and stores no cursor.
- Delivery is at least once and resumes from a cursor after reconnect. Cursors and the event log are stored on the server, so they survive a server restart. An event commits with the change it reports, so a server that stops before storing it delivers it at its next start.
  - A subscriber acknowledges the events it has handled, and its stored cursor moves only then, never backwards. A subscription with no explicit cursor resumes after the stored one.
- Rosen's events and the channel's events (R13) share one log, one sequence and one cursor per subscriber. A claim release and the land that caused it are always delivered in order, to subscribers on any machine.

### R10 · CLI
- The `rosen` commands are `import`, `change new|list|show|abandon`, `commit`, `status`, `diff`, `log`, `claim|share|wait|release`, `overlaps`, `review comment|approve|resolve|list|mark|landed|failures`, `receipt submit`, `land`, `rebase`, `resolve`, `workspace list|delete|watch`, `server start|status`, `run`, `config show`, `events`, `machine join|list|approve|revoke`, `machine key create|list|revoke` (R14) and `mcp`.
- `--json` on every command, with versioned output schemas. Each output line has a `schema` ID (`rosen.<shape>/v1`); incompatible shape changes bump that version. `--json-schema` prints the offline JSON Schema catalog (`crates/rosen-cli/schemas/v1.json`), including nested records and refusal variants. Usage and runtime failures, including retried workspace watcher failures, use `rosen.error/v1` with `command` (null for usage errors) and `error`. Help and version requests remain text.
- `--help` is complete enough that an agent can learn Rosen from it alone.
- `rosen mcp` serves the commands as Model Context Protocol tools on stdin and stdout, for an agent host to start. Each tool is one command, named by its words joined with `_`, with the command's arguments and help as its inputs, read from the same definitions `--help` prints. A call runs that command with `--json` and returns its output; a failure or refusal is an error result holding its `rosen.error/v1` object. `--workspace <DIR>` runs the commands in that workspace. Commands that run until something happens elsewhere (`wait`, `events`, `workspace watch`) and the operator's commands (`import`, `server start`, `machine`) are not tools. `review approve`, `receipt submit` and `land` are tools only with `--landing`.

### R11 · History queries
- The server answers log, path history, blame, diff, merge base and file read at any commit or change through the API, with no checkout.
- It derives and caches the indexes these need from landed commits.
- **Accept when:** a reviewer can review a change and a checker can fetch its merge result without materialising a workspace.

### R12 · Post-land verification
- The project configures a **post-land check set** (the full tests). External checkers run it (D9). After-land projects also run `checks.pre_land` (build and lint) after landing. `post_land_next` offers test work; `post_land_build_next` offers build work. Jobs carry their check kind and immutable configured commands; results are checked against both. The two streams have independent passing prefixes, so a passing build never marks full tests green.
- **Batches.** The server offers checkers the newest untested landed commit. One passing run marks every commit up to it **green**, and the server records the last green commit.
- **Failure and bisect.** On a failing run, the server offers the commits between the last green and the failure for bisection, until one commit is found to break, the **culprit**.
  - Bisection jobs persist their captured landed interval and a step token. Each result must name the exact offered commit, check kind and token; duplicate or stale results are refused. The server splits the remaining interval at its midpoint, then requests a second failure of the culprit and a fresh passing run of its parent. Contradictory confirmation stops the session for the checker to investigate. Sessions resume after restart.
- **Record every confirmed failure.** Both build and test culprits are persisted as `post-land-failure` records and events with their check kind and output, queryable through `post_land_failures` and `review failures [--change <change>]` after restart. Repeated confirmation is idempotent. A recorded test-failure batch is not offered endlessly as untested and is never marked green merely because it was recorded.
  - Records and events are deduplicated by `(culprit commit, check kind)`, including confirmation by different bisection sessions. Completed batches remain covered when their culprit already has a record. Later test searches use the newer of the test green and the latest recorded, non-reverting test culprit before the failing batch as their lower bound. This does not mark the bound green; the new culprit still needs a fresh passing parent confirmation.
- **Auto-revert.** In after-land mode only a **build** failure requests a revert; a **test** failure stays landed with its failure record for Velocity to file as an issue. Before-land projects keep reverting confirmed full-test failures. The mode is resolved at the culprit's landed commit, like its check commands; a configuration edit takes effect once it lands. The server lands a revert of the culprit through R8, as a server-owned change that needs no receipt or approval. The culprit change goes back to `open` with its owner, carrying the failing check output, and gets a `reverted` event. Its commits and workspace are kept.
  - The inverse waits for the culprit's original post-land work to finish and merges against the current base, preserving later lands; an overlapping inverse that cannot merge cleanly refuses without moving the base. The inverse land, reopened change and durable failure output commit atomically. Repeating a confirmed culprit returns the same revert, and its reopened change can land again under the same change ID after repair.
- A flaky result is the checker's concern: a failure is confirmed only after the culprit fails twice and its parent passes. Required build reverts run immediately after confirmation; recovery retries an interrupted inverse.
- **Accept when:** an after-land test failure is bisected, recorded and left landed; an after-land build failure is recorded and reverted, its change reopens with its work intact, and later independent work is preserved. Before-land full-test failures retain their existing automatic revert behavior.

### R13 · AIRC channel on the server
The server holds each project's AIRC channel, so agents on every machine coordinate through one source of truth. AIRC's behaviour (claims, events, targeted delivery, messages, message modes and ledgers) is as Velocity SPEC F14 defines it. Rosen is its store and its authority.
- **State.** The channel's state lives in the server's metadata store:
  - **piece claims** on work items (`task:<id>`, `issue:<n>`, `spec:<section>`, or the task text);
  - **file claims, shares and waits**, which are Rosen path claims (R6);
  - **events** and agent **messages** with their `to` and `intent`;
  - **presence**: the nicks joined, their machine, and each one's message mode;
  - the **Discoveries** and **Past work** ledgers.
- **Piece claims** are first-claim-wins, each in one transaction, like exclusive path claims. A refusal names the holder and the time of its claim. A claim is kept through failure and disconnects, and released as Velocity F14 says.
  - A piece is locked by its identity, or by its task text when it has none. The holder claiming again extends its claim and keeps the original claim time.
  - A release drops only the caller's own pieces: one, or all of them.
- **Presence.** A member joins with the member ID, nick and machine Velocity gave it. A nick names one joined member at a time. Leaving keeps the member's piece claims. Rejoining keeps its message mode, so a restart does not lift a quarantine.
- **Messages.** Recipients are resolved and fixed when a message is sent.
  - A message naming an unknown nick is refused whole. Only the user's comments may name no one, and they then reach every joined member.
  - A heads-down member's messages from other agents are held until Velocity releases them or the member returns to open mode. They are delivered after its read cursor, so none is skipped.
  - A quarantined member gets nothing from other agents and its messages reach nobody. Its piece claims are frozen: it cannot take, extend or release one.
- **One log.** Channel events and Rosen's events share one ordered log and one cursor per subscriber (R9). Targeted delivery follows Velocity F14: an agent receives only the lines it must act on.
  - Channel lines use the `channel` event kind with the channel payload in `detail`. Their recipient agent identities are fixed at publication; an empty audience reaches only the project view. They use the same subscription and acknowledgement API as Rosen events, including over the network transport.
  - Each channel write commits in one transaction with its lines, so a stored change never lacks its line. A delivered message's line targets its recipients by nick. Joins, leaves, mode changes, claims, refusals, releases and ledger entries reach only the project view, so an agent is pushed only what it must act on.
- **Velocity keeps the tools.** Velocity serves AIRC's tools to every agent as now, with the member ID and nick fixed at launch, and calls the server through `rosen-client` for each one. No machine keeps channel state of its own beyond its delivery cursors.
- **Server unreachable.** Claims and messages need the server, as landing does. A tool call made while the server is unreachable fails with that reason. It is never answered from a local copy.
- **Accept when:** two agents on different machines that claim the same piece or an exclusive path at the same moment never both succeed; an event or message reaches its recipient on another machine within 1 s while both machines reach the server; and no two machines ever see different claim holders.

### R14 · Network access and enrollment
Machines join a project with no login, monitor or remote desktop on the joining machine, so headless machines can be added from a script.
- **Network listener.** The server listens on a TCP port with TLS, alongside the local transport. Its certificate is created when the project is created. Daemons on other machines connect to it, and serve their own machine's clients over the local transport.
- **Join keys.** The project owner creates a join key from any enrolled machine, through Velocity or `rosen machine key create`. A join key has an expiry, a use limit and a role (agent machine or checker), and carries the server's address and the fingerprint of its certificate.
- **Zero-touch join.** A machine joins with one non-interactive command, such as `rosen machine join <key>` in an install or provisioning script, or a machine image.
  1. The daemon connects to the server and checks the server's certificate against the key's fingerprint. On a mismatch it stops before sending the key.
  2. It exchanges the key for the machine's own **machine credential**, sending its receipt public key, which the server binds to the machine as it issues the credential (R8 step 1).
  3. It stores the credential encrypted (Windows: DPAPI through Credential Manager). The client rotates it automatically before it expires.

  The machine never uses the join key again. Credentials last 30 days; the daemon checks hourly and renews during the final seven days. A lost rotation response can be retried with the prior credential until its original expiry. The server stores only credential hashes. Windows Credential Manager holds the encrypted enrollment; `upstream.json` holds only a reference, address and certificate fingerprint. The server's `network/identity.json` (its TLS private key) and `upstream.json` are created readable and writable by the current OS user only (Windows: a protected access list naming that user and SYSTEM; Unix: mode 0600), whatever the data directory allows. Enrollment and pending requests alone are accepted without an authenticated machine; every other network request rechecks the machine's current status.
- **Existing enrollment files.** Before reading an existing `network/identity.json` or `upstream.json`, the daemon reapplies the same owner-only permissions, including to files created by older versions. If it cannot protect the file, loading fails before the identity or upstream settings are used. Repair preserves the file contents and does not automatically rotate the identity, keeping enrolled certificate pins valid. A previously accessible key must be treated as possibly disclosed: permission repair cannot undo prior access; recovery from suspected compromise requires replacing the identity and re-enrolling machines.
- **Approval.** A machine that joins with a valid key is admitted at once. A machine that asks to join without one waits as **pending** until the owner approves it from an enrolled machine.
  - `rosen machine join --address <host:port> --fingerprint <SHA-256>` requests pending admission without a key. `--name` names the machine and `--data-dir` selects its local daemon data directory. The pending credential is stored encrypted; approval activates it without another join. A revoked machine must enroll again and cannot be reactivated by approval. Because anyone who reaches the listener can ask, at most 64 requests await approval at once, at most 4 from one address (an IPv6 /64 counts as one); a request past either limit is refused until the owner approves or revokes some. An unapproved request expires, and is removed, 7 days after it was made.
- **Machine list and revocation.** The server lists every machine with its role, last contact (to the minute) and running agents. Revoking a machine refuses its credential on its next request. Its changes, claims and workspaces are kept, as for a failed change.
- **Discovery.** On a local network, daemons find the server by DNS-SD (mDNS), so a key without a reachable address still works there.
  - The listener advertises `_rosen._tcp.local.` with its certificate fingerprint. Joining tries the key's address first, then matching LAN announcements; every candidate must pass TLS certificate pinning before receiving the key. `machine key create --address` can supply an address reachable from the joining machine.
- **Agents.** Every agent on a machine works under that machine's credential. Velocity names each agent (its nick) and its role when it starts the agent's session, as AIRC does now. Owners, reviewers and receipt submitters are recorded as machine plus nick. The request names only the nick, which may not contain `@`; the server takes the machine from the connection's credential, or `server` for its own machine. `rosen change show` and `rosen review list --approvals` show `<nick>@<machine>`. Changes and approvals recorded before machines were kept show the bare nick.
- **One enrollment for Rosen and Velocity.** Velocity's cross-system dispatch uses the same join key, so one command adds a machine to both (§9).
- **Accept when:** a headless machine joins from one command with no interactive step; a revoked machine's next request is refused; and a daemon that meets a certificate other than the key's fingerprint never sends the key.

## 5. Done means (v1)

- R1–R14 are built and run on Windows 11. The Linux build compiles.
- **The stress run passes on at least three Windows 11 machines**, enrolled with one join key and no interactive step, one of them serving the project:
  - 100 concurrent agents spread across the machines, each creating a change (some stacked), editing, claiming, submitting receipts and landing, over at least 1000 lands;
  - a new workspace is ready in under 2 s (p95) with the warm pool filled;
  - a land with a valid receipt commits in under 200 ms (p95);
  - automatic snapshot latency is reported as samples, p50, p95, maximum and the count over R2's 2 s budget, separately from pass/fail checks; each new stress change attempts to start its watcher and waits for its initial scan before measuring edits, then verifies the acknowledged snapshot's immutable commit contains every expected edit;
  - watcher startup, measurement and shutdown errors or timeouts are counted as `snapshot_failures` with diagnostics, without aborting the change; a valid sample is kept even if shutdown fails, and an explicit snapshot still makes the change's edits durable before landing;
  - no edit is lost, no land is applied twice, and the base moves only by a clean land (plus matching receipt and approval in before-land mode), or a server revert;
  - an injected failing commit is bisected and reverted, and its change reopens with its work intact;
  - no two agents ever hold the same piece or exclusive path claim, on any machine;
  - the run is repeated with the server, machine daemons and clients killed at random points, and with the server unreachable from some machines for a period, and still meets those guarantees.
- Velocity can create workspaces, claim pieces and paths, message agents, stack changes, review, submit receipts and land through `rosen-client` alone, with no git worktree, GitHub PR or local AIRC files in the loop.
- The proofs on the proof list check, and each is tested against its fixture table. Merge is also checked against `git merge-file` on a differential corpus.
- `cargo build --workspace`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` pass, as does `lake build` in `proofs/`.

## 9. Velocity changes Rosen needs

Rosen depends on these changes to Velocity. They are built in Velocity's repository, not here.

- **Worktrees.** Threads get workspaces from `rosen-client`. The worktree warm pool (F5), its prebuild worker and `git worktree` calls go. Rosen prepares pool workspaces (R3). The project's prepare commands take over Velocity's toolchain, Lean cache and prebuild steps. Velocity keeps the per-agent steps after a take: copying untracked files, linking skills and its after-take setup command. A swarm launch raises the pool size on the machines it uses.
- **PR watcher.** GitHub polling every 15 s (F6) is replaced by the Rosen event stream.
- **PR duty.** Before-land duty agents review, approve, submit receipts and land through `rosen-client`. After-land projects land named changes without those gates; review/scout agents follow landed events and record coverage. Branch updates (F6) become conflict probes for overlapping edits; stack restacks remain server-side rebases (D19).
- **AIRC.** Velocity's AIRC tools and view call the Rosen server (R13) instead of local files. File claims, shares, waits and overlap notices become Rosen path claims (R6). Task claims, events, messages, presence and ledgers become channel state on the server.
- **Rebases.** Velocity asks `rosen-client` to apply a pending server rebase at the agent's step boundary, or while it is parked, in place of `airc_rebase` (R2).
- **Enrollment and dispatch.** Velocity creates join keys and lists, approves and revokes machines through R14. Its cross-system dispatch uses the same join key, so one command adds a headless machine to both Velocity and Rosen.
- **Dependency waits and parking.** Most waits become stacked changes. Parking remains only for path-claim waits.
- **Build queue.** Velocity keeps its build queue. Before-land projects produce pre-land receipts with priority; after-land projects build after landing. Both run full tests and typed bisection (R12), filing recorded test failures and promptly processing required build reverts.
